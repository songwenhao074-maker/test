# 协议015原生流分布检查与待审批方案

日期：2026-09-05。状态：检查完成；以下修正和后续训练均未实施。

## 结论

当前证据支持“离线与在线环境、特征语义及任务动态显著不一致”，并发现归一化退化和图输入对容器身份处理不足。尚未发现已保存轨迹的原始标签、容差标签、实际迁移与容器身份对齐错误。不能把问题概括为原生模拟器产生了无效数据，也不能把D低分直接解释为在线遗忘。

本次只读取协议004训练/开发数据、源代码及已完成的301小试轨迹，并进行冻结模型的内存中敏感性检查。没有采集新轨迹、训练或更改模型权重、修改模拟器、使用预留测试或改写原小试结果。

## 检查证据

### 1. 离线与在线使用了不同工作负载及资源尺度

| 项目 | 起始checkpoint的离线环境 | 原生在线小试 |
|---|---|---|
| 工作负载 | OfflineTraceWorkloadV2 | BWGD2 |
| 数据来源 | 固定202步、16槽位的qos数组 | 筛选出的42条Bitbrain VM轨迹、随机到达任务 |
| 每容器CPU最大需求（已观察） | 1,860 IPS | 7,242.43 IPS |
| 每容器磁盘需求中位数 | 1,000 MB | 2 MB |
| 四个I/O特征 | 所有容器恒为1 | 原始网络/磁盘吞吐的缩放值 |
| CPU主机容量 | 3,223.2 IPS | 4,029 IPS |
| 磁盘主机容量 | 8,053 MB | 32,212 MB |
| 额外资源设置 | RAM×2、磁盘×1000、CPU容量×0.8、磁盘容量×0.25 | 原生值 |

离线CPU还经过LOAD_SCALE=1.5、截断到100及IPS_RATIO=18.6，RAM乘RAM_FACTOR=1.4；这些不是在线BWGD2的转换公式。因此仅恢复几个容量倍率并不能保证两种工作负载等价。

在线39.79%的容器CPU输入超过离线训练容器CPU最大值。容器I/O输入的归一化最大值可达44.41，而离线这四列均恒为1。原生容器磁盘归一化最大值仅0.000333，离线最大为1。图分支的容量缓冲适配并不会自动消除时间编码器、路由器和预测头的这种输入失配。

进一步核验：离线五个训练块、三个开发块的逐容器需求数组逐项完全相同，变化来自模拟器调度和运行结果。旧开发分数主要衡量同一底层短轨迹下的调度变化，不能据此推断对BWGD2新任务流的泛化能力。该局限不改写已验收消融结果。

来源：[离线工作负载](../simulator/workload/OfflineTraceWorkloadV2.py)、[离线采集](../dump_replay.py)、[离线manifest](../artifacts/ftmoe_end_to_end/data/protocol_004_physical/manifest.json)、[原生工作负载](../simulator/workload/BitbrainWorkload2.py)。

### 2. 第14台主机存在退化归一化统计

离线使用每主机、每特征的训练最大值归一化。主机索引13（第14台）的RAM、磁盘训练最大值为0，最终分母为1e-8；CPU分母只有2 IPS。原生流中该主机出现普通负载，归一化后的最大CPU/RAM/磁盘分别约为3,621、2.09×10¹¹、3×10⁸。这些值仍是有限数，因而通过了现有“非NaN/Inf”检查，但已经严重超出训练尺度。

仅在内存中用离线训练集跨主机同特征最大值替换退化分母，对相同冻结A模型重新推理；没有使用在线标签计算归一化统计：

| 诊断输入 | 全程F1 | 后半程F1 |
|---|---:|---:|
| 原输入，独立重算 | 0.456718 | 0.412500 |
| 仅RAM、磁盘零分母兜底 | 0.456233 | 0.412071 |
| 再处理CPU=2的底值分母 | 0.469613 | 0.422414 |

原输入重算概率与保存预测完全一致。兜底处理对部分概率影响很大，但总体F1改善有限；它是需要修复的健壮性问题，不能单独解决本次低分。此表是事后敏感性诊断，不是新在线方法成绩，也不是已选定的正式归一化策略。

来源：[归一化实现](../train_ftmoe_end_to_end.py)、[诊断记录](../artifacts/ftmoe_online/distribution_audit_015/normalization_probe.json)。

### 3. 原生流的资源类别覆盖有结构性限制

当前300步原始标签异常306，全部CPU；主容差标签异常555，也全部CPU。CPU/RAM/磁盘最大实际需求容量比分别为2.4813、0.50065、0.0002794。

BWGD2把磁盘占用固定成1、2、3 MB。最多16容器，即使每个3 MB且全部放在一台主机，磁盘需求也仅48 MB，远低于32,212 MB。因此当前原生设置不可能产生磁盘容量异常，延长运行也解决不了这一点。RAM本次没有过载，但尚不能推断其他原生流必然没有RAM过载。

原始Bitbrain字段提供磁盘读写吞吐量，并没有磁盘空间占用字段；BWGD2的磁盘占用是工程假设。另外，代码把网络接收/发送吞吐填入名为RAM read/write的两个输入；Memory usage除以4000也包含资源缩放，并非仅KB到MB的单位转换。后续需明确这些字段含义，不能把磁盘吞吐直接当作磁盘空间。[Bitbrain官方字段说明](https://atlarge-research.com/gwa-t-12/)

### 4. 没有发现已保存标签错位，但拟调度和执行语义确实不同

独立重算原始物理标签、±1容差标签，与保存值不一致数均为0。实际迁移事件与前后落点一致，存活容器身份无错位，时间编号连续，输入均为有限值。动作前主机资源由容器需求重聚合后的最大绝对误差为0.000977，符合float32累加的舍入尺度。

300步共有647项拟迁移、450项实际迁移。4.17%的动作前活跃容器落点与拟调度不同或部署被拒绝；涉及4.75%的主机间隔。现有标签按实际结果生成，并没有把拒绝迁移记成已执行。

冻结A在拟调度聚合未受影响的4,572个主机样本上F1仍只有0.449970，所以调度差异不能单独解释全部低分。

图分支还存在另一项语义问题：它将相邻拟调度矩阵的同一槽位当作同一容器。原生流中513次相邻槽位目标变化，有365次发生于容器身份改变或槽位空缺，不能视为同一容器迁移。图的occupancy还会计入空槽位的随机调度行。真实容器ID和存在标记已经采集，但当前模型接口尚未使用。这个问题应在共同输入层处理，不能只给D修正。

来源：[图编码](../recovery/PreGANSrc/src/ftmoe_ablation.py)、[采集入口](../prepare_ftmoe_online.py)、[审计JSON](../artifacts/ftmoe_online/distribution_audit_015/findings.json)。

### 5. 原生数据有检测信号，长期遗忘场景却未建立

以动作前主机CPU/RAM/磁盘需求是否超过真实容量作为简单因果规则，无需训练，本流全程原始标签F1=0.963780、主容差标签F1=0.723982。它不是完美预测：动作后的任务结束、实际迁移和容差标签会带来差异；也不是本实验新增竞争方法。诊断表明不能用“原生数据随机、无法检测”解释模型约0.46的全程F1。

另一个按拟调度聚合当前需求的规则，原始F1=0.782383、容差F1=0.640548；在旧开发三流上同口径容差F1分别约0.9204/0.9265/0.9448。输入与目标关系也随工作负载变化。

BWGD2按第11条记录的CPU需求筛选VM，新任务从该VM轨迹的开头开始，任务完成后再次创建任务。延长模拟时间主要增加从同一筛选池抽取的任务，并不等价于连续读取真实VM数日的时间演变。原生长期运行本身不保证存在非平稳变化，更不保证普通微调持续退化。

## 方案比较（待审批）

### 方案A：先修正共同输入，再建立原生同域起点（推荐）

目的：把“刚上线就跨环境失配”与“上线后长期保持能力”分开检验。

1. 登记新协议和输出目录，完整保留015失败结果与014归档。制定同一份训练/在线数据契约：七个字段的实际含义、单位、容量、任务身份、时间编号、拟调度与已执行历史、标签成熟时刻。
2. 归一化仅由训练数据确定。对未覆盖或仅有CPU底值的主机资源列使用训练集同类主机/同特征统计兜底，并记录名单；不根据在线结果选截断阈值，不动态重算线上最大值。加入数值尺度报告，避免只检查NaN/Inf。
3. 给共同图输入增加有效槽位及身份连续性掩码，空槽不计occupancy，身份替换不计同一容器迁移。历史执行信息只使用此前已发生的数据，当前仍用预测时可见的拟调度；不得输入当前动作结束后的落点。离线与在线使用同一版本。
4. 在独立原生训练/开发流上，对五个已归档v4分别作共同离线适配，之后每个种子四组共享同一个适配后checkpoint。归一化、共同离线选模和预算先冻结。也可选择从头训练v4，但需要单独登记；本轮不同时搜索两条路线。
5. 先用模型种子1做共同起点验证及300步四组小试；通过后才完成五种子的共同起点及原开发、正式流程。B/C/D在线更新预算、D动态专家条件、0.65与D>B的最终目标保持不变。新流程的共同起点已改变，需明确命名，不能冒充“原014权重直接上线”。

数据划分按底层VM身份或互不重叠的原始时间段登记，不能仅换随机种子却反复复用同一批轨迹开头；训练/开发/正式划分先于模型比较。现有BWGD2不支持这种来源划分，需要一个显式的工作负载接口扩展。因此这一步也属于待审批的模拟器/数据流程变化。301已被诊断使用，后续用于新协议开发，不作为新确认数据；旧预留测试及201–205仍不使用。

收益：输入健壮性、共同起点和线上任务一致，比较更聚焦长期保持能力。代价：需要新增共同离线适配，且不能提前保证D优于B。原生磁盘类别问题仍须如实限制结论，不以扩大压力强行补类别。

### 方案B：保留原014起点，恢复与离线一致的受控环境

统一旧OfflineTraceWorkloadV2的映射、容量、I/O语义与任务机制，先做旧开发流的顺序输入一致性检查，再扩展连续长流。

收益：更接近原消融环境，减少起点失配；无需把历史checkpoint转换为原生同域适配模型。局限：原qos底层数组只有202步，不能直接支撑2,000步；必须先找到/构建有独立来源的连续长轨迹。不能循环拼接202步，也不能只恢复四个倍率就宣称同分布。旧倍率属于既有合成基准设定，需公开说明，不能表述为原生环境。

适合希望论文所有实验维持同一受控基准的情况。当前不建议在尚无合适长轨迹时直接实施。

### 方案C：在共同起点合格后，增加独立的长期变化场景

先采用原始时间戳连续推进的VM片段，观察自然变化。若用户希望额外研究受控变化，再单独登记VM组合变化或资源需求变化的时间表、强度和数据划分；所有方法共享轨迹，变化参数只由工作负载依据或训练数据确定，不能按D−B结果选择。

它是对A或B的后续补充，不能替代起点与输入修正。若研究磁盘异常，需要先确定目标是空间不足还是I/O瓶颈；前者需要另外的占用数据或公开的合成需求假设，后者需要重新定义容量与标签。两者都会改变实验问题，须单独审批。

## 建议审批范围与验收顺序

建议先批准方案A的共同数据契约、归一化健壮性及身份掩码修正，并登记原生数据划分和共同离线适配预算；待共同起点与小试完成，再决定是否需要方案C。不要立即扩大原015到五种子，也不要只增加学习率或注入漂移。

实施后依次验收：保存数据可重建输入和标签；零需求列不会导致病态归一化；空槽/新任务不会制造同一容器迁移；四组初始输出相同；未来标签和落点不影响过去预测；再评估独立原生开发流的初始检测能力。若共同起点仍明显偏低，先报告，不继续长流确认。

继续采用延迟标签下先预测后学习的顺序评估。参考样本不参加更新，原始/容差标签同时报告；当前301诊断不能作为独立统计证据。[River渐进评估说明](https://riverml.xyz/dev/api/evaluate/progressive-val-score/)

自然流上B可能保持稳定，D也可能不优于B。方案的目标是建立有效、公平的比较条件，不承诺制造预期走势。
