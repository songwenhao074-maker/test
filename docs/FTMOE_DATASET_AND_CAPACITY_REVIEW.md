# 在线异常场景：数据集与容量方案评审

日期：2026-09-05。范围：资料调研、代码核验、已保存轨迹的静态敏感性分析。没有下载完整数据集、修改模拟器或重启模型实验。协议014归档、015/016结果保持不变。

结论：可以通过合理资源配额与真实需求波动形成CPU、RAM、磁盘空间过载；新数据集也有合适候选。但“生产资源轨迹”“有故障注入标签的数据”和“当前三类物理过载标签”不能直接互换。任何方案都不能保证普通微调退化、D优于B。

## 1. 已核验的数据集

| 候选 | 字段和时间覆盖 | 接入价值 | 局限与建议 |
|---|---|---|---|
| Google clusterdata-2011-2 | 约12,500机器、29天；任务CPU、内存、本地磁盘空间使用量；通常300秒使用量窗口 | 最值得核验的长期三资源真实轨迹；可由任务级数据重建需求，再交给GOBI生成公共回放 | 不是直接可用的三类过载标签；磁盘为归一化单位，未公开逐机器磁盘容量，需登记模拟容量映射；缺失率、空间字段非零覆盖需下载小样本验证 |
| Alibaba cluster-trace-v2017 | 容器请求CPU/RAM/磁盘空间及使用比例；主机容量与使用量；事件24小时，使用量只公开连续12小时 | CPU/RAM/空间语义吻合，适合先做短流真实性验证 | 容器磁盘使用为可缺失字段；300秒口径约144间隔，无法支撑2,000步长流，不能循环后声称多日独立轨迹 |
| Alibaba cluster-trace-v2018 | 4,000机器、8天；容器CPU、内存、网络和磁盘I/O利用率 | 适合长期CPU/RAM工作负载 | disk_io_percent是I/O繁忙度，不能作为磁盘空间；第三资源需独立空间模型，或另立I/O异常任务并重新适配模型 |
| RCAEval | 多个微服务系统的CPU、内存、磁盘I/O、网络等故障案例，有注入时间和根因注释 | 适合带标签的外部故障验证 | disk案例是I/O压力；输入为服务指标/日志/调用链，不能直接替换BWGD2容器需求；案例流不等于连续2,000×300秒生产轨迹 |

Google来源：[官方2011说明](https://github.com/google/cluster-data/blob/master/ClusterData2011_2.md)、[Google作者的v2格式与schema文档公开副本](https://www.researchgate.net/profile/Auday-Al-Dulaimy/post/Are-there-any-datasets-for-cloudSim/attachment/59d61de379197b807797be3e/AS%3A273823268573184%401442295962733/download/Google%2Bcluster%2Busage%2Btraces.pdf)。后者明确区分本地空间和I/O时间，并说明不含大部分分布式持久存储。逐机器磁盘容量未提供。官方v2.1链接的网页预览无法读取；实际接入仍应以下载时schema及字段检查为准。全量约41GB压缩，不建议本机一次解压全部。I/O时间字段约仅前14天有数据，与空间字段是两个概念。

Alibaba来源：[2017说明](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-v2017/trace_201708.md)、[2017 schema](https://raw.githubusercontent.com/alibaba/clusterdata/master/cluster-trace-v2017/schema.csv)、[2018说明](https://github.com/alibaba/clusterdata/blob/master/cluster-trace-v2018/trace_2018.md)、[2018 schema](https://raw.githubusercontent.com/alibaba/clusterdata/master/cluster-trace-v2018/schema.txt)。2017需按实例ID和有效时间连接请求与使用比例；缺失不能填成正常。机器soft/hard error或任务failed不能不经核验直接映射为CPU/RAM/空间过载。2018全量约49GB压缩，宜流式筛选。

RCAEval来源：[官方仓库](https://github.com/phamquiluan/RCAEval)、[作者数据卡与案例字段](https://huggingface.co/datasets/phamquiluan/RCAEval)。先下载一个系统的少量案例核验，避免直接拉取全部多模态数据。

这些资料证明字段与用途具有潜力，尚不证明选定子集具有足够三类异常。源系统已经限流或OOM时，观测使用量也不等于未受限需求。若重新调度到较小模拟容量后产生过载，应称“真实轨迹驱动的模拟过载”，不能称源数据原有故障标签。

## 2. 降低容量：可行，需真正重放

本地依据：`simulator/environment/RPiEdge.py`与`simulator/Simulator.py:getPlacementPossible`。CPU和磁盘已有容量缩放；RAM当前没有对应容量开关，需要新增明确配置。RAM需求乘数与RAM容量不是同一个参数。部署检查要求当前CPU、RAM空间、磁盘空间需求不超过剩余量；RAM/磁盘I/O检查已注释，降低I/O带宽不会直接生成当前三类空间过载标签。

固定降低容量可以解释为容器可用配额、操作系统保留量或较小硬件配置。例如RAM可用量取现有配置的75%或50%。磁盘应解释为容器数据分区配额，不能将约32GB物理磁盘任意缩成几MB且不说明。

原生BWGD2磁盘空间仅固定1–3MB：有效初次部署后需求不增长，固定容量不变、所有迁移继续合法准入时，单靠降低初始容量无法产生空间过载，通常增加拒绝部署。协议016已有动态磁盘，因而降低容量可能在后续增长时触发过载；RAM本身也随时间变化。

对016已保存300步及一个确认间隔，只改容量分母重算标签，结果如下。没有改变原标签文件，没有运行模型。

| 静态假设，相对016 | 主异常占比 | 主CPU/RAM/磁盘计数 |
|---|---:|---:|
| 原容量 | 2.90% | 106 / 3 / 30 |
| 仅RAM容量×0.75 | 3.65% | 106 / 39 / 30 |
| 仅RAM容量×0.50 | 5.23% | 104 / 117 / 30 |
| 仅磁盘容量×0.75 | 6.98% | 91 / 3 / 241 |
| 仅磁盘容量×0.50 | 17.17% | 58 / 3 / 763 |

**这些数字不是重跑结果，也不是模型F1。** 需求、落点和生命周期被固定；真实降低容量会影响准入、GOBI和后续执行，因此不能用重标旧轨迹代替新实验。类别按最大超载比例选取，可能因资源竞争而改变；±1步容差沿用016实现。

静态结果表明磁盘对容量很敏感，但容易变成磁盘主导；RAM减半也可能让RAM超过CPU。不能只凭总异常比例达标就认为分布大致相似。建议先做单因素容量对照，保留016原容量作控制；候选值预登记，依据数据覆盖、部署成功率、持续时间和资源比例筛选，不用D−B或模型F1挑容量。

可重算脚本与机器结果：`artifacts/ftmoe_online/scenario_review_20260905/capacity_screen.py`、`capacity_screen.json`。脚本校验原容量标签与保存值完全一致。

## 3. 其他方案，按接入成本依次评估

1. **扩大现有Bitbrain任务画像覆盖：低至中成本，优先。** 原生筛选只用一个时刻的CPU门槛，将本地499条CSV缩到42条。改用开发时段完整画像挑选CPU型、内存型、混合型任务，保留同一VM的跨资源对应关系与连续性。能够改善RAM上尾，不会补出源数据不存在的磁盘空间。形式上是工作负载构成改变，应保留筛选规则、任务ID及选择概率。正式时段不能按其异常标签挑任务。
2. **固定资源配额敏感性：低成本，优先。** 如上所述，保持16主机/16槽位、CPU映射、到达规则与调度器，分别改RAM或磁盘。新轨迹必须从起点重新生成，四组共享。合适的场景应同时有正常期、异常期和恢复期，并记录拒绝部署/迁移。
3. **状态式磁盘占用或内存增长：中成本。** 用任务阶段、缓存积累、日志新增与清理形成连续变化，比独立跳变更容易解释。磁盘可写成“上期空间+新增保留数据−删除数据”；写入吞吐量不能全部当成空间增长，覆盖写不会持续占新空间。已有016 Markov磁盘属于合成部分，可以另设机制对照，但不能覆写016或称原始Bitbrain磁盘数据。
4. **外部后台负载/可用容量变化：中成本。** 模拟同机后台任务、缓存或其他租户占用。可用容量等于物理容量减后台占用，或把后台需求加入总需求，两者不可重复扣减。要让四组获得同样的相关输入，并由实际需求和实际容量算标签。随时间改变容量属于明确的受控漂移，原015不覆盖实施；本轮只评审。
5. **真实长轨迹替换：中至高成本，长期优先Google 2011。** 先小样本核验磁盘非零覆盖、缺失、长任务长度和单位；再实现任务级适配器，保存ID和时间来源，GOBI重新生成轨迹。先分开发/正式连续区段，再在开发区段定映射和容量。三条正式流若共享原任务/时间必须披露相关性。Alibaba2017适合短验证，2018需额外处理空间语义。
6. **隔离环境故障注入：高成本，作为外部验证。** 真实CPU压力、内存增长、磁盘占用/清理可以获得机制明确的测量记录。Chaos Mesh支持CPU/内存压力；Chaosd区分磁盘读写压力与空间填充：[StressChaos说明](https://chaos-mesh.org/zh/docs/simulate-heavy-stress-on-kubernetes/)、[磁盘压力说明](https://chaos-mesh.org/docs/simulate-disk-pressure-in-physical-nodes/)。本机资源有限且为Windows，适合另用受限Linux实验环境。物理磁盘满/OOM会在使用量超过硬限制前失败，故障时段标签和当前“需求>容量”标签必须分别定义，不可机械互换。

不优先单纯提高到达率：016实际运行容器均值约15.26，已经接近16上限。进一步加到达量可能只增加拒绝；降低主机数或增加槽位又涉及当前16×16模型和调度结构适配。也不建议取消准入检查或故意削弱GOBI来取得想要的模型比较。

## 4. 与在线微调结论的关系及建议顺序

第14主机的退化归一化、槽位更换容器被当成迁移的问题，不会由容量调整或新数据集自动消失。016后验兜底已经表明单独修复归一化不是全部解决方案，但四组共同输入修正仍需单独核验并登记。若新场景冷启动仍显著不适配旧模型，需要讨论共同离线适配；不能假定换数据后原014权重保持0.9。

建议下一次审批具体选择：先采用现有016动态磁盘，做预登记的RAM/磁盘单因素容量对照；同时将任务画像筛选列为容量对照失败后的独立方案。两者不在同一次实验里一起变，便于解释。长期数据真实性路线优先Google2011小样本审计，Alibaba2017作短验证，RCAEval作额外故障案例验证。

所有方案先检查数据本身：正常/异常支持数、各资源计数、异常持续长度、资源联合分布、缺失与部署成功率。沿用“大致相似”要求，不强求完全一致；也不为制造B下降而选择场景。通过数据检查后才做四组相同初始权重、同一回放的先预测后学习。新场景通过不代表动态专家贡献成立，仍分别检验D>B与D>C。
