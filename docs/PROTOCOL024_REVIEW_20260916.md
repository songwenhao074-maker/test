这轮已有真实动态机制：v2a 第二预算接受4个专家；v2b出生2次、退役3次、复用2次。它解决了上一轮“根本不触发”的问题，但没有建立有实用幅度的 D 优势。

## 已确认：birth 按“新增”验收，部署却做“替换”

调用链：

1. v2b 继承 `PeriodicResidualLifecycle._buffer_train`，调用 `bank.preview_with_shadow`。
2. 新生候选的预标签验证和独立 guard 也调用同一 preview。
3. preview 使用“所有当前 active IDs + shadow”；已有 specialist 时，模型为四个 generalist + 旧 specialist + 新 specialist。
4. v2b 接受后交叉渐变，把旧 specialist 退役；最终部署只有四个 generalist + 新 specialist。

因此训练、验收、guard 的承诺与部署拓扑不符。复用路径的 `_preview_specialist` 已经使用四 generalist + 待复用 specialist；主要缺口在 birth 的三条继承路径。不能只修验证函数，漏掉 shadow loss 与 guard。

合成反例使用真实 bank、等路由权重：四通用专家异常logit均为−2，旧 specialist 为10，新 specialist 为1。对一个正样本：

- live logit=0.4，CE=0.513015；
- birth preview logit=0.5，CE=0.474077，改善约7.59%；
- 实际替换后 logit=−1.4，CE=1.620417。

这证明“预览改善”不能保证实际替换改善。它没有证明本轮两个具体接受事件都受到同样幅度影响；该影响应由新开发版本重放核验。脚本见 `maintenance/reproduce_protocol024_v2_preview_20260916.py`。

## 调度、匹配与恢复检查的实际限制

**机会记账不完整。** v2b 的 on_matured 在训练、验证、冷却和渐变阶段直接return，只有monitoring才判断是否到达reuse/birth时点。日志的49次reuse_opportunities因此是进入monitoring后看到的机会，不是所有理论到期机会。reuse_skipped_busy初始化为0，没有对应增加路径；不能由“0 busy skips”推断没有资源争用。

已计入的49次中：2次无记忆、37次不匹配、10次验证，最终2次接受。37/49说明匹配是重要的实际筛选环节；不等于把阈值放松就会提高AP。centroid先把16主机表示汇总，再做时间均值，可能掩盖局部故障服务；q10阈值也是单个记忆窗口内的自相似统计，并未校准跨复现的检索能力。应检查被拒绝的记忆是否真实有用。

**不能把专家ID直接当作response law专长。** 两次birth接受的是最早的ID4、5。结合固定600/856成熟步提议与128+32训练验证，代码时序提示它们都可能在R1_first内形成；须用原ledger确认训练/验证区间。若成立，当前只有两个早期R1相关记忆，不能当作R1/R2/R3三个专长均已存储的复现实验。第一次完成复用的checkpoint时间索引为4123，已到R3_rec1；这一点可由stdout核验。

**恢复检查比字段名窄。** runner恢复后仅比较4个预测并统计updates/events是否增加；没有逐张量核对下一次Adam更新、没有比较下一事件完整内容及其恢复轨迹。如果更新发生在第4次预测之后，当前循环甚至没有检查更新后的下一预测。因此 `checkpoint_recovery_verified=true` 只支持已做的短预测一致性检查，不支持完整恢复证明。

**终点有未决候选。** v2a首预算和v2b均为created=accepted+rejected+1。应明确标为stream_end_censored，不能补判拒绝、补读未来标签或把它藏在completed字段后。

**测试覆盖不足。** v2b三项单测主要检查常量、向量归一化与配置值，没有验证birth部署等价、忙碌机会计数和完整恢复。现有workflow success不能替代这些链路验证。
